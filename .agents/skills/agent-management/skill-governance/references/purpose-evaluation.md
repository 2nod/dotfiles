# 目的別評価の方針

この文書は、比較実験と保存済みの証拠からskillの効果や採否を判断するときに使う。
指示の棚卸し、重複整理、参照の修正は [スキルと指示の見直し](skill-review.md) から進める。
文書保守の完了と、効果の実証、runtimeへの配布完了を区別する。

`.agents/eval-catalog.json` にskillごとの目的、証拠、必要なシナリオ、スクリプト化候補を置く。
本文と食い違う場合は本文から目的を再確認し、台帳を更新する。

- 合否を定義する前に、そのskillが何を改善するためにあるかを説明する。
- 通常、境界、使わない方がよい例を用意する。個別案件の正解をskill全体の目的と混同しない。
- 成果物の正確性、手順の証拠、読み手にとっての品質、発火の妥当性を区別する。
- 決定論的verifierは自動実行し、意味の解釈は目的別rubricで証拠付き採点する。キーワード一致を意味理解の代用にしない。
- TDDのred→greenや診断のフィードバックループは実行traceで確認する。最終出力だけから推定しない。
- verifierは未修正fixtureで失敗し、最小修正で成功することを確認する。別の正しい実装を不当に拒否しない。
- 品質の後に所要時間と使用量を比較する。変更行数とclass数は補助指標であり一律の報酬にしない。
- 旧ケース、実測不足、環境エラー、条件混在、未採点は保留する。差が見えないことを不要の証拠にしない。
- 本文、参照ファイル、fixture、verifier、モデル、runnerが変わったら古い結果を採否へ流用しない。
- 自動出力は候補に留める。無効化前に複数シナリオの実測、代替、例外を確認し、判断理由をroundのdecision.jsonへ記録する。
- installed skillは利用可否を判断する。ローカル候補を付けない。別名wrapperを作る場合は自作skillとして別に評価し、upstreamを直接変更しない。

反復処理や実行の不確実さが失敗原因にある場合は、script化を検討する。
抽出する場合は入力、出力、失敗時の扱い、再実行時の副作用、検証方法を定義する。
実験planのscript_reviewにはdecision（extract/defer）とreasonを記録する。
deferでは理由だけでよく、extractの場合に限り入出力、失敗、再実行、検証方法を必要とする。
この記録のためだけにscriptを追加しない。

実行方法と保存先は `agent-observability/README.md` を参照する。


## 改善ループの実行規約

比較実験を行う場合は `agent-observability/skill-loop.py` を入口にする。
計画ごとに新しい保存ディレクトリを作り、`plan.json` と実測ログを残す。
計画の書き方とコマンドは `agent-observability/README.md` の「改善ループ」を参照する。

| 段階 | 行うこと | 次へ進む条件 |
|---|---|---|
| 目的と評価設計 | 本文から目的を確認し、ケースが測る範囲と測れない範囲を記録する | 各ケースの目的との対応、verifierの検証証拠、モデル、回数、採点者、上限を記入し、planチェックが成功する |
| 予備評価 | 無効と現行を同じ入力で1ペア以上比較する | 成果物とtraceを保存し、rubricの各項目を証拠付きで採点する |
| 原因の切り分け | 失敗を評価設計、実行環境、skill指示に分ける | 指摘箇所と原因を記録する。ケースの誤りならケースを直し、新しい条件で評価する |
| 修正案 | 原因に対応した最小の変更を別ディレクトリに用意する | 変更する指示と期待する挙動を示す。script化する場合は入出力と失敗、再実行、検証方法を記録し、見送る場合は理由を示す |
| 再評価 | 無効、現行、修正版を同じ条件で比較する | 通常例、境界例、負例で各3ペア以上。修正に使っていないholdoutを含め、reviewチェックが成功する |
| 判断と監視 | 継続、修正継続、修正版採用、無効化、保留を理由付きで記録する | decisionチェックが成功し、適用範囲と次に確認する条件が記録されている |

`screen` は問題発見用であり、継続、修正版採用、無効化の根拠にはしない。
`validate` は全ケースを事前に選び、失敗したケースも判断対象に残す。
holdoutは修正案を作る材料に使わないケースを事前に指定する。
結果を見て修正したら、そのケースはholdoutではなくなるため、新しいケースと計画を用意する。
3ペアは運用上の最低条件であり、統計的な確証を意味しない。

採点は成果物とtraceを読んで行い、AI採点、人による採点、条件を伏せた採点の別をreviewerに明記する。
修正版採用は、全ケースで目的を達成し、現行が失敗した比較が少なくとも一つある場合に判断できる。
効率だけの改善は、実行前にplanのefficiencyへ指標、最低削減率、品質維持の検証根拠、閾値の理由を記録する。
通常・境界・非適用と独立holdoutを含むvalidateで各3回以上実行し、全比較ペアで現行と候補の品質合格と指定幅以上の削減が必要。
平均だけの改善やscreenだけの結果では採用しない。項目とコマンドはagent-observability/README.mdを参照する。
無効化には無効条件での全ケース達成に加え、代替手段、例外、戻し方の検討を必要とする。
同点だけを無効化理由にしない。

## 比較する範囲と条件

判断が必要なskillと変更仮説を選び、全skillの再実行を初期条件にしない。
モデル、runtime、共通指示、候補の見せ方を固定し、条件別に集計する。
共有skillでは対象モデルごとに確認し、一つのモデルの結果を別モデルの採否へ流用しない。

runnerの既定は対象skillの明示注入（explicit）。名前とdescriptionからの選択はcatalogモードで別の計画として比較する。
catalogは隔離環境の選択課題であり、native discoveryや常時提示される全候補、複数turnの効果を保証しない。
実環境の発火を判断する場合は、そのruntimeのdiscovery条件を再現する別の評価計画を用意する。

候補の短縮、参照分離、手順の削除が、誤発火、不要な読み込み、途中停止、成果物の品質をどう変えるかを目的に結び付ける。
品質と依頼の完遂を確認した後に時間と使用量を比較する。
既存のvalidate、holdout、人手レビューの条件は文書保守の検査で置き換えない。

## 実行と記録

実行は `run` を使う。
開始時に計画と呼び出し上限を予約するため、同じディレクトリで二重実行できない。
中断、timeout、失敗時はログを確認し、既に消費した回数を含めて範囲を見直してから新しい計画を作る。
開始記録の削除による再試行はしない。
モデル、目的、skill本文、参照、ケース、verifier、runnerの変更は別の評価条件として扱う。

チェックは記録の存在、版の一致、比較組、採点の完了と採否の最低条件を検証する。
目的の妥当性、証拠の意味、holdoutの独立性は採点者が確認する。
チェック成功を品質の保証や外部送信の許可として扱わない。
有料評価の実行はユーザーが依頼した範囲内に限定し、通常の定期点検では実行しない。

## 適用と継続監視

判断結果は実測ディレクトリの `decision.json` に残す。
共有台帳は目的と評価設計を管理する。ローカルの実測パスや採否はコミットせず、各roundの記録とレポートで確認する。
修正継続や保留では、欠けている証拠と次の一手を残す。
採用判断と実際の配置変更を区別し、配置後の内容が評価した修正版と一致することを確認する。
installed skillのローカル修正は別名wrapperに置き、upstream本文を直接変更しない。

skill-scoutで採否や評価進捗を扱う場合は、対象の保存済み計画に対するcheckと既存auditを使う。
条件更新、採点不足、悪化、新たな採用候補があれば、次の作業と証拠を示す。
定期監視は新しい有料評価や台帳の採否変更を自動実行しない。
変化がない場合は通知しない。

## 人手によるデザイン評価

見た目、文章構成・表記の統一、情報の探しやすさを目的に含むスキルは、機械検査とAIによる内容採点だけで採否を確定しない。台帳のhuman_review_requiredで対象を宣言し、keep/adopt/disableの判断には人手レビューを必要とする。hold/reviseで不足を記録することは可能。

比較画面に同じ入力、基準テンプレート、なし・あり・修正版の出力を同じ表示条件で並べる。Markdownは整形後の表示も比較し、原文を別途読めるようにする。HTML/SVGは実際の描画を比較する。コードや見出し名の一致は補助検査であり、読みやすさの代用にはしない。ブラウザ制約で描画を確認できない場合は人手確認待ちとする。

人は、構成・表記の一貫性、必要情報の探しやすさ、読みやすさ、重複・空欄の有無について、対象出力と具体的な理由を記録する。AIは人の記録を捏造・代筆して完了扱いにしない。採点者が人かどうかの真正性自体は機械検査だけでは保証できない。

デザイン以外の目的も個別に検証する。操作系は実行後の状態と保持すべきデータ、診断系は原因特定と復旧、レビュー系は正しい指摘・誤指摘・見逃し・不要な変更・必要提案、計画系は制約充足と実行可能性を確認する。品質が揃った後に時間・使用量を比較する。
