# プロジェクトへの適用

## 規則を三層へ分ける

| 層 | 内容 | 置き場所の例 |
| --- | --- | --- |
| 共通原則 | 所有、権限、固定入力、証拠、復元、失敗への制御 | 共通skill。常時適用が必要なものだけagentの実行時指示から参照 |
| 作業別手順 | Git引き渡し、比較評価、長時間処理、外部操作 | 専門skillまたは既存の運用文書 |
| プロジェクト固有契約と設定 | 権限の付与、担当、状態名、provider、上限、合格基準、command | 既存の規約、config、schema、validator |

権限を付与する正本は一つにし、skill側で承認範囲を再定義しない。
具体的な数値やサービス名を別案件へコピーせず、その値が守っていた条件を抽出する。
現在の値、過去の結果、停止済みの運用は共通skillへ移さない。

## 導入手順

1. 対象規約を読み、各規則が防ぐ失敗、適用条件、正本、機械検査の有無を整理する。
2. 重複、矛盾、旧手順、説明と実装の不一致を分ける。文書調査だけで実装の一致を主張しない。
3. 共通原則へ残す部分と、既存の専門手順へ委ねる部分、固有設定へ残す部分を決める。
4. 利用者が依頼した範囲だけを変更する。skill作成の依頼から元プロジェクトの規約変更を推測しない。
5. 実行規則を変更する場合は、正本、廃止する規則、適用開始、既存作業の扱い、検査の変更を揃える。

移行後の確定履歴は、その時点の証拠として保持する。
新規の規則は一つの正本を指し、同じ条文を複数箇所へ再掲しない。

## 必要な工程だけを選ぶ

| 作業 | 適用する境界 |
| --- | --- |
| 小さな可逆編集 | 所有対象と既存差分の確認、変更に応じた検証 |
| 複数担当の実装 | 依存、writer、対象の版、引き渡し証拠 |
| 比較実験 | 結果前の条件固定、試行の識別、判定不能の扱い |
| 長時間または外部処理 | 停止条件、費用、再試行、副作用の照合、回収と復元 |
| 手順の改訂 | 正本と検査の整合、移行、旧失敗の再現確認 |

独立review、複数session、専用台帳、毎回の全件検証は共通の必須条件にしない。
既存規約が要求する場合、または具体的なリスクに対して必要な場合に適用する。

## 導入結果の確認

小さな変更、承認済みの操作、入力変更後の引き渡し、結果不明の外部処理に当てはめて読む。
小さな変更で工程が増殖せず、承認済みの操作は進み、古い証拠では次工程へ進まず、外部副作用を重複させない判断になるかを確認する。
追加した条件は次の例でも照合する。

| 状況 | 必要な判断 |
| --- | --- |
| 依存先は完了したが実行環境が旧版 | 依存を解除せず取り込みと検証を先に行う |
| 確認データの結果を見て候補を調整した | 探索用へ移し、独立確認待ちにする |
| 評価経路が壊れたまま品質指標が上がった | 採用を保留し、同じ経路の修復か診断へ戻る |
| 保存できるが中断復元で結果が変わる | 厳密継続を主張せず、本実行前に復旧条件を直す |
| 修正後も旧失敗が検査を通る | 対策未完了として制御を修正する |
| 同じ目的で次の仮説を試す | 予算と継続条件を確認し、作業単位を再利用して新しい試行を記録する |

文章の見出しや語句が揃うだけでは行動の検証にならない。
既存の機械検証を使い、必要な新規検証は観測可能な結果を判定する。
