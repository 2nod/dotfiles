# オーケストレーションとタスクsession

複数の担当へ作業を分ける場合に使う。
小さな作業は一つのsessionで完結させ、分割する場合は全体の調整を担うsessionを一つ決める。
ここでいうsessionは継続して文脈を持つ作業担当であり、特定製品のtaskやthread APIを指定するものではない。
作成や委任には利用環境で許可された手段を使い、独立した利用者向けtaskの作成条件と内部subagentの委任条件を混同しない。

## 役割と所有

| 担当 | 所有する判断と作業 | 他の担当へ渡すもの |
| --- | --- | --- |
| オーケストレーションsession | 全体目標、作業分割、依存順、担当割り当て、進捗確認、証拠の受け入れ、次工程の開始判断、全体完了 | 固定入力、所有範囲、権限の根拠、完了条件、修正依頼 |
| タスクsession | 割り当てられた範囲の調査、実装、検証、成果物、判断の記録 | 対象の版、検証結果、成果物、残作業、阻害要因 |
| 実行専用のタスクsession（必要時） | 固定入力での実行、停止、結果保存、回収、許可されたcleanup | 実行結果または失敗境界と証拠 |
| レビュー専用のタスクsession（必要時） | 固定対象への独立した確認 | 対象の版と結び付く判断、指摘、証拠 |

分割後のオーケストレーションsessionは調整を担当し、タスク所有のcodeや成果物を横から編集しない。
不具合は元の担当へ戻す。
担当を交代する場合は旧担当の停止と成果物の保存を確認し、所有範囲を明示して移管する。

merge、公開、課金、外部実行の権限は役割名から得られない。
既存規約が許可する担当だけが実行し、オーケストレーションsessionは必要な証拠と順序を確認する。
独立reviewや実行専用sessionの要否は既存規約と作業上の必要性から決める。

## 1. 全体の出口と分割を決める

オーケストレーションsessionは利用者が必要とする成果と、全体完了の条件を既存planへ固定する。
既存taskとsessionを確認し、同じ目的を持つ担当がいれば再利用する。

作業は、独立して検証できる成果物と所有範囲で分ける。
依存関係がある作業は順番に開始する。
並行できるのは、入力が揃い、変更対象、共有出力のwriter、外部resourceが競合しない作業だけとする。
同じfileへ並行して書く担当は作らない。

既存planや台帳には、作業、担当session、所有範囲、依存、次の一手、完了証拠を対応付ける。
新たな台帳形式やsession数を一律に要求しない。

## 2. タスクsessionへ割り当てる

オーケストレーションsessionは[作業契約の雛形](../templates/work-contract.md)の該当項目を使い、次を渡す。

- 全体目標のうち今回が満たす成果と、対象外。
- 正本の参照、固定入力、対象の版、作業場所、所有するfileやartifact。
- 依存成果が実入力へ取り込まれた証拠。
- 既存の実行権限と停止条件、必要な場合は費用や時間の上限。
- 必須検証、完了条件、返却先。

taskの委任は、権限の拡大や追加の再委任を自動的には許可しない。
委任されたsessionは入力と所有範囲を確認して作業を開始する。
不足を見つけた場合は具体的な阻害要因を返し、不足に依存しない許可済みの作業を進める。

## 3. 作業と進捗確認を続ける

タスクsessionは割り当て範囲を検証まで進める。
準備中の不具合や通常の修正は同じsessionと作業単位で直す。
判断が変わった場合、阻害要因が出た場合、引き渡し可能になった場合に、証拠と次の一手をオーケストレーションsessionへ返す。

オーケストレーションsessionは利用可能な通知や待機機能を使って結果を追う。
進行中の担当へ同じ依頼を再送せず、変化のない状態を高頻度で読み直さない。
待機中は依存しない調整を進める。
利用者の追加指示は全体目標へ反映し、影響する担当へ変更点を伝える。
実行中の入力に影響する変更は、停止と再検証の境界を確認してから渡す。

sessionのidleや応答終了を成果の完了とは扱わない。
応答が止まった場合は、実行中の処理と保存済み成果物を確認してから再開または担当移管を決める。
同じ処理が生きている状態で代替担当を実行させない。

## 4. 結果を受け取り、次工程を決める

タスクsessionは、成果物、対象の版、検証結果、未確認事項、残作業を返す。
オーケストレーションsessionは完了条件と証拠を照合し、次の処理を選ぶ。
以下は判断の区分であり、既存の状態名やschemaを置き換えるものではない。

| 受け取った状態 | オーケストレーションsessionの次の操作 |
| --- | --- |
| 条件を満たす証拠が揃った | 成果を受け入れ、必要な統合と入力照合後に依存先を開始する |
| 修正や検証が不足 | 不足条件と対象の版を示し、同じタスクsessionへ差し戻す |
| 外部判断や権限が不足 | 準備済みの具体的な操作と不足理由を利用者へ示し、独立した作業は継続する |
| 実行失敗や結果不明 | 失敗境界を確定し、原因に依存する後続を止めて診断へ戻す |

修正後は変更された対象に必要な証拠を取り直す。
前の版の検証結果で新しい版を通さない。
担当内の完了と全体完了を区別し、必要な後続がある場合は受け入れだけで作業を終えない。

## 5. 反復と全体完了

改善を続ける場合は、確定結果から次の仮説と入力を決め、予算と継続条件の範囲で同じ担当を再利用する。
反復ごとにsessionやPRを増やさず、詳細は[境界ごとの判断](execution-boundaries.md)の「改善の反復」に従う。

オーケストレーションsessionは、統合後の実際の対象、全体完了条件、必要な外部状態、成果物の所在を確認する。
実行や回収が依頼に含まれる場合は、その結果まで確認する。
全体条件を満たすか、利用者が停止を指示するまで調整を続ける。
外部入力待ちで継続できない場合は、完了とせず、再開条件と担当を保存する。
環境が将来の自動再開を支援していない場合、自動で再開すると約束しない。

終了前に、不要になった実行や資源が残っていないことを確認し、許可された終了処理を担当へ渡す。
利用者には全体の成果と検証結果、残る制約を報告する。

## 例

```text
オーケストレーション
  ├─ 実装session A：対象を修正 → 検証証拠を返す
  │    ↑ 不足条件を示して差し戻し、同じ担当で修正
  ├─ 証拠を受け入れ → 権限に従って統合 → 実入力を照合
  └─ 実行session B（必要時）：固定入力で実行 → 保存と回収
       ↓
     オーケストレーションが全体完了条件を確認
```

実装Aと実行Bには依存関係があるため、この例では同時に開始しない。
独立した調査が必要なら、所有範囲と入力が分離できることを確認して並行させる。
