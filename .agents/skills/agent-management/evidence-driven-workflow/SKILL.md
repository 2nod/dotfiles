# 証拠に基づく作業進行

次の操作を、所有者、許可範囲、対象の版、完了証拠から決める。
既存の正本と作業単位を使い、進行のためだけにtask、PR、承認待ちを増やさない。

## 適用する範囲

最初に利用者の目的、残作業、既存規約、既存の承認を読む。
小さな可逆変更は対象と確認結果の記録で足りる。
複数担当の引き渡し、外部操作、長時間処理、比較評価がある場合に、該当する境界だけを追加する。
このskillは権限を付与せず、新しいsession、branch、台帳、独立reviewを一律には要求しない。

## 六つの原則

1. **所有範囲**：変更対象と担当を決める。共有出力のwriterを一つにし、既存差分を保護する。
2. **権限**：操作の対象、送信先、費用、破壊範囲を既存承認と照合する。承認済みの範囲は進め、不足する境界だけを確認する。
3. **固定入力**：判断に使う入力と合格条件を検証前に決める。比較では仮説と変更要因も固定する。
4. **証拠付き遷移**：対象の版と結び付く証拠で次へ進む。未実行、欠損、error、判定不能を成功に含めない。
5. **復元可能性**：失うと再作業になる成果物は、保存に加えて読込や復元を確認する。
6. **失敗への制御**：最後の成功境界と最初の失敗境界を特定し、証拠で支持される原因へ検査や手順変更を当てる。

## 進め方

- sessionを分ける場合は[オーケストレーションとタスクsession](references/session-orchestration.md)を読む。調整担当が割り当て、進捗確認、証拠の受け入れ、差し戻し、後続開始を全体完了まで担う。
- 実作業では[境界ごとの判断](references/execution-boundaries.md)の該当節を読む。改善を続ける場合は「改善の反復」で継続と停止の境界を決める。準備不具合は既存作業内で直し、必要な証拠が揃った次の操作を実行する。
- 規約の一般化や導入では[プロジェクトへの適用](references/project-adaptation.md)を読む。共通原則、作業別手順、固有設定を分ける。
- 引き渡し情報が散在するときは[作業契約の雛形](templates/work-contract.md)から必要項目だけを既存planやissueへ組み込む。新規台帳は作らない。

Git操作、タスク管理UI、非同期jobの具体的操作には、利用可能ならそれぞれ`git-workflow`、`task-lifecycle`、`async-workflow-operations`を使う。
それらの正本や承認条件をここで再定義しない。

## 完了

利用者が求めた成果、対象に対応する検証結果、成果物の所在、残る制約を示す。
担当間の引き渡しを全体完了と呼ばず、後続作業が必要なら担当と開始条件を残す。
