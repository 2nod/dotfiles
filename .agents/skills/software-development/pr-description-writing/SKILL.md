# PR本文の作成

レビュワーが「なぜ変えるか」「どう変えたか」「何を確認したか」「何を変えないか」を順に判断できる本文を作る。
`templates/pull-request-description.md` を構造として使い、空の任意節とコメントは提出前に除く。

## 根拠の収集

1. baseとの差分、commit、関連issueや仕様、実行済みの検証、画像や動画を確認する。
2. 実装とテストを現在の挙動の根拠にする。
   issueや議論は変更理由と要求の根拠に使い、現行実装と食い違う記述をそのまま採用しない。
3. 確認できないリンク、変更理由、検証結果、影響範囲を補わない。
   不明点が本文の正確さを変える場合は、本文案に混ぜず確認事項として示す。

## 各節の役割

- **背景と課題**：現在の挙動、利用者への影響、今回達成する状態を書く。
  関連リンクだけで説明を済ませない。
- **実装詳細と変更点**：採用した方針と、その方針で要求を満たせる理由を書く。
  不採用案は実際に検討した場合だけ挙げ、具体的な破綻条件や影響範囲を添える。
  変更ファイル一覧は、差分が大きくレビューの案内になる場合だけ折りたたむ。
- **確認項目**：利用者から見たQA項目と、コマンドによる開発検証を分ける。
  実施済みだけを`[x]`にし、コマンドと結果は確認できた値をそのまま書く。
- **その他の備考**：スコープ外、既知の制約、付随修正、後続作業を書く。
  該当事項がなければ節ごと省く。

## 本文の点検

- commit一覧や全ファイルを写すのではなく、レビュー判断に必要な責務と挙動を説明する。
- 同じ内容を背景、実装、備考で繰り返さない。
- 画像や動画は、見れば判断できる変更に限って実装節の冒頭に置く。
- 付随修正は変更理由と検証を分けて書き、主変更に紛れ込ませない。
- 追加commitやレビュー対応後は、本文が現在の差分と検証結果に一致するか再確認する。
- GitHub上の本文更新は外部状態の変更として扱い、依頼または明示許可を得てから行う。
