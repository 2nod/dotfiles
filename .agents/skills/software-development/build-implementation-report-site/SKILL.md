# レビュー用実装ブリーフ作成

`writing/html`を表示基盤として、変更を知らないレビュワーが、変更後の挙動、変更ファイル、注意点、検証の範囲を少ない読み返しで理解できるHTMLを作る。
冒頭に変更の要約と短いファイル別説明を置き、変更目的ごとに実コードの差分と検証根拠へつなぐ。
文章量や指定レイアウトへの一致だけで読みやすさを判断しない。
比較実験の詳細は`software-development/build-experiment-report-site`へ分ける。

## 作成要否

- ユーザーがHTMLまたはSite形式の実装・検証レポートを明示的に依頼したときだけ作成・更新する。
- 「実装して」「修正して」「テストして」「PRにして」「実装が完了した」といった依頼や、作業結果の報告だけでは、レポート依頼とはみなさない。
- レポートを作るか迷う場合は作成せず、変更内容・検証結果・未検証事項をチャットで簡潔に伝える。
- 通常の実装、修正、回帰テスト、E2Eの依頼だけでは、このskillを使わない。
- レポートの依頼がなくても必要な検証は行い、変更内容・結果・未検証事項をチャットで簡潔に伝える。

## Skillの階層

- 内容、証拠、読む順序、保存先はこのskillを優先する。HTMLの部品、コード強調、差分、印刷の表示要件は`writing/html`に従う。
- 初稿前に、発見済みの実体pathから`writing/html/SKILL.md`と`design-system/component-samples.html`を読む。共有`document.css`と必要なアセットを成果物へ同梱して読み込む。ページ固有CSSは配置調整に限る。
- 題名、要約、表、図、折りたたみを必要に応じて選ぶ。固定の節数、右サイドナビ、ディレクトリツリーを必須にしない。
- 複数ファイルの変更は短い一覧で役割と変更を示す。配置や移動が判断に関わる場合は`writing/show-me`の変更マップも参考にする。
- 説明用スケッチと実コード差分を明記して区別し、図でコードの根拠を置き換えない。

## 完了条件と保存先

- 以下の完了条件と作業手順は、HTMLまたはSite形式のレポートを明示的に依頼された場合だけ適用する。他のskillからの参照や実装・PR・マージの完了を作成の契機にしない。
- 依頼されたレポートは、実装と必要な検証後、最終回答の前に作成または更新する。
- 既定は`$CODEX_HOME/visualizations/<日付>/<task-id>/<report-name>/index.html`へ保存する。
- レポートと画像は製品リポジトリ、stage、commit、push、PRへ含めない。
- 最終回答ではレポートの絶対パスまたはURLを示す。

## 作業手順

1. baseと変更後の版、trackedとuntrackedの差分、設計、テスト、計測成果物を確認する。SHAがなければ未提示とし、提供されたコードsnapshotを根拠にする。
2. 冒頭に対象の役割、変更後の挙動、重要な注意点、検証の範囲を短くまとめる。続けて主要な変更ファイルごとに、役割、変更内容、影響または確認点を示す。多数のファイルは目的別にまとめ、全変更への参照を詳細に残す。
3. `templates/report-outline.md`を参考に、変更目的ごとのまとまりを作る。一つの目的を複数ファイルが実現する場合は、関連差分を同じまとまりで説明する。複数段階にまたがる変更は、ファイル一覧の後に必要な全体フローを置く。
4. 各まとまりから変更前後の挙動、判断に必要な実コード差分、注意点、テスト証拠を追えるようにする。入力、拒否条件、副作用、状態遷移は、その変更の理解に必要な範囲を説明する。項目名と順序を一律に増やさない。
5. 実装済み、自動テスト、ローカルE2E、未確認を区別する。検証結果と保証範囲は見える位置に置き、長いテストコード、生成物、完全なログは詳細にまとめる。失敗や未確認、契約を変えるテスト・生成物の変更は要約から隠さない。
6. コード移動と処理内容の変更を分ける。移動前後の内容に加え、import、呼び出し元、設定への影響を確認し、移動検出だけで挙動不変と断定しない。
7. 重要な主張をBefore / Afterの実コードと、実ファイルのテスト証拠へ結ぶ。テストごとに固定する契約、前提、期待結果を示し、テストが直接確認した範囲を越えてUIや運用の成立を断定しない。
8. 同じ変更の説明を要約、全体集計、詳細で繰り返さない。既存レポートの再構成では、有効な根拠を詳細に保ち、古い結果だけを更新する。
9. 共有CSSと必要なアセットの同梱・読み込みを確認し、実ブラウザでリンク、ID重複、横溢れ、デスクトップとモバイルを確認する。認知負荷の改善を実測したと書くのは、人手の理解度や読み返しなどを実際に測った場合だけにする。
