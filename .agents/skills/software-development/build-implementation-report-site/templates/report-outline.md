# レビュー用実装ブリーフ構成

## 00 レビュー用実装ブリーフ

00だけで、対象が何をするものか、誰がいつ使うか、何を変え、どこを読み、レビュワーが何を判断するか分かるようにする。
設計の全履歴や全ファイルの説明はここに置かない。

### 読み始めるための文脈

PR、issue、会話を開かなくても変更を解釈できる最小限の文脈を置く。

1. 対象の役割を一文で示す。
2. 利用者または運用者と、変更が関係する発火条件を示す。
3. 代表的な入力から出力までを一例で示す。
4. 内部名を使う場合は、読者向けの名称と対応付ける。

背景史や周辺機能の網羅説明は不要である。
コードリンクは文脈の代わりにせず、リンク先で確認できる責務を本文に書く。

### 変更範囲マップ

変更ファイルをディレクトリ構成へ投影し、レビュワーがどこから読むかを示す。
全リポジトリのtreeや全ファイル一覧は置かず、変更領域と、その役割を理解するための入口、呼び出し先、契約、テストだけを示す。

変更領域ごとに次を対応付ける。

1. pathまたは責務単位のまとまり
2. 全体の中で担う役割
3. 変更種別。追加、変更、移動、削除
4. 関連する入口、呼び出し先、契約、テスト
5. この領域をレビューする理由

ディレクトリ自体の追加、削除、移動がある場合は、baseと変更後の最小構成を並べる。
構成を変えていない場合は、変更後の最小構成だけを示し、各pathへ変更種別と役割を添える。
pathから役割を推測せず、実コード、設定、参照関係から確認する。

### 変更の要約

最初の画面には次の順で置く。

1. 変更目的を一文で示す。
2. 主要な変更を責務単位にまとめ、「変更前」「変更後」「目的」「変更方法」に分ける。
3. 変えていない互換経路、責務、データ境界を示す。
4. レビュワーに判断してほしいことを示す。なければ「追加判断なし」と書く。
5. 検証結果と保証範囲を一行で示す。実測結果には分母と計測条件を併記する。

この段階では、未定義の領域記号、略語、内部IDを使わない。
記号が説明を短くしない場合は導入しない。
製品の実行時挙動の変更と、その根拠となるテスト、文書、レポート、検証ハーネスの変更は分けて示す。

### レビュー導線

主張ごとに、変更領域、全体での役割、何をなぜどのように変えたか、検証結果、レビュワーの判断事項を結ぶ。
表の行は責務または確認したい主張にし、ファイル一覧にはしない。

| 変更領域と役割 | 変更・目的・方法 | 検証 | 判断 |
| --- | --- | --- | --- |
| `src/jobs`：再実行対象を選ぶ | 指定項目だけを選別する条件を追加し、他の項目の処理を防ぐ | `test/...`、実測値 | 追加判断なし |

差分量や全差分に占める割合が判断に役立つ場合だけ示す。
割合は工数、重要度、リスクの割合ではないと明記する。

### レビュー結果

判断が必要な事項、確認済みの主張、未確認の範囲を短く示す。
H/P/Uのタグを使う場合は、最初の表示で名称を定義し、タグだけを読ませない。
タグが導線を短くしないなら使わない。

必要なら主張に `H1`、`P1`、`U1` のようなIDを付け、詳細へのリンクに使う。

## 詳細の補足

詳細は00の主張を確認するために必要なものだけ置く。
設計書のように全章を埋めず、HTMLでは折りたたんでよい。

次の項目から必要なものだけを使う。

1. **重要差分**：責務、ガード、契約、状態遷移が変わる箇所の実コードBefore / After
2. **実行フロー**：文章と差分だけでは追えない入力、分岐、外部I/O、失敗位置、出力
3. **契約と不変条件**：schema、API値、正規化alias、拒否条件、複数箇所のガードが作る保証
4. **検証**：コマンド、ケース別結果、実測値、手動確認手順、未確認範囲
5. **運用境界**：feature flag、互換性、rollback、実環境や未変更consumer

各補足の冒頭に、対応する主張と主要コードを短く示す。
00のレビュー導線へ戻れるリンクを置く。

### レビュー根拠の残し方

- 責務、ガード、契約、状態遷移が変わる箇所は、baseと変更後の実コードを並べる。概念上のBefore / Afterだけで代用しない。
- Beforeにはbase SHA、対象path、該当行を示す。Afterにはcurrent commitまたはworking tree、対象path、該当行を示す。base側へ直接リンクできない場合は、その制約を明記し、現在のファイルへのリンクで代用しない。
- コード比較ごとに、変更前の責務、変更後の責務、利用者または運用へ生じる効果を書く。差分と無関係なimport、型注釈、表示要素は省略してよい。
- 全ファイルを比較対象にせず、00に置いた主張をコード上で閉じる比較へ絞る。
- schema field、API値、設定、locale aliasなど列挙値が契約になる場合は、値、役割、適用範囲、拒否条件を表にする。
- 競合防止、再送安全性、完全一致検証など複数箇所で成立する保証は、不変条件の一覧から各コード比較、フロー、検証へたどれるようにする。
- 既存レポートの再構成前に、コード比較、契約表、不変条件、検証成果物を棚卸しする。古い件数や未確認表記は現状へ更新し、現在も有効な根拠は維持する。

## 図示方針

- 静止図だけで主要経路、分岐、終端が読めるようにする。
- 実行コストが異なる処理と外部I/Oを視覚的に分ける。
- 図からレビュー導線と必要な補足へ移動できるようにする。
- 動きを使う場合は、方向、同時性、反復の理解を補う用途に限る。
- reduced-motionでも配線、状態ラベル、終端を残す。

## 表示方針

- 変更要約は幅500px前後でも横スクロールなしで読めるカードまたは縦積みにする。
- 横スクロールは、契約表や比較表など列の対応そのものが重要な箇所に限定する。
- 画像、SVG、カード、コード欄をビューポート外へはみ出させない。

## 小さな変更

小さな実装では、00の文脈、変更要約、レビュー導線、検証結果だけでよい。
重要差分、契約表、不変条件、図は、判断に必要な場合だけ追加する。
