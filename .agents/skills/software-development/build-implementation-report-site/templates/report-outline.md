# レビュー用実装ブリーフ構成

## 1 レビュー概要

最初の画面だけで、レビュワーが変更の重要性と読む順序を判断できるようにする。

### 変更目的と判断事項

次を短く示す。

1. 解決する問題と、変更後に達成する状態
2. 利用者または運用への効果
3. レビュワーに判断してほしいこと。なければ追加判断なしと書く
4. 主なリスク、未確認事項、rollbackの要否
5. 検証結果と保証範囲

差し止め、要判断、未確認の項目がある場合は、対応する変更単位へ移動できる短い一覧を置く。
ここでは内容を再要約せず、項目名、重要度、状態だけを示す。

### 読み始めるための文脈

PR、issue、会話を開かなくても変更を解釈できる最小限の文脈を置く。

1. 対象の役割
2. 利用者または運用者と発火条件
3. 代表的な入力と出力
4. 内部名を使う場合の読者向け名称

背景史や周辺機能の網羅説明は不要である。
コードリンクを文脈の代わりにせず、リンク先で確認できる責務を本文に書く。

## 2 変更マップ

変更ファイルを責務へ対応付け、レビュワーがどこから読むかを示す。
ディレクトリは場所を示す手掛かりであり、責務の根拠にはしない。

各変更責務へ短い安定IDを付け、次の3箇所で同じIDを使う。

1. 全体の処理経路の各段階
2. 変更マップの各行
3. 後半の責務別変更と根拠

処理段階が複数の責務に支えられる場合は複数IDを示す。
実行に必要でも差分で挙動を変えていない段階は、変更責務へ見せず「既存境界」として区別する。

変更領域ごとに次を示す。

1. pathまたは責務単位のまとまり
2. 全体の中で担う役割
3. 関係する入口、呼び出し先、interface、設定、テスト
4. 変更種別。追加、変更、移動、削除
5. この領域をレビューする理由

複数ディレクトリや横断的な変更では、関係が分かる最小の表または図を使う。
ディレクトリ自体の追加、削除、移動がある場合だけ、baseと変更後の最小treeを並べる。
単一モジュール内の小さな変更では独立したマップを省き、次の変更単位へ役割とpathを含める。
全リポジトリのtreeや、役割を説明しない全ファイル一覧は置かない。
baseからの各変更ファイルが、いずれかの変更単位またはその証拠へ一度は対応していることを確認する。

差分量を示す場合は `git diff --numstat` 相当を根拠にし、次を満たす。

1. 各変更ファイルを一つの主責務へ一度だけ割り当てる
2. 責務別の変更行数と全差分に対する割合を示す
3. 責務別行数の合計が全差分行数と一致する
4. 製品コード、テスト、生成物など内訳の意味を示す
5. 差分量は工数、重要度、リスクの割合ではないと明記する

一つのファイルが複数責務を持ち、機械的なファイル単位集計が誤解を生む場合は割合を出さず、主要変更箇所を行範囲で示す。

## 3 責務別の変更

変更をファイル単位ではなく、利用者またはシステムへ一つの効果をもたらす責務単位にまとめる。
見出しには変更マップと同じ安定IDを置き、処理経路と変更マップへ戻れるようにする。
各変更単位は次の順にする。

1. **役割**：全体の中で何を担う領域か
2. **変更前**：変更対象だった挙動、制約、問題
3. **変更後**：成立する挙動または契約
4. **目的**：なぜこの変更が必要か
5. **変更方法**：どの責務、条件、データ、状態遷移を変えたか
6. **影響と未変更境界**：利用者への効果、互換経路、変えていない責務
7. **証拠**：主要コード、テスト、実測、未確認範囲
8. **レビュー項目**：レビュワーが確認または判断する点。各項目に重要度、状態、理由、根拠を付ける

重要度と状態は別の軸として扱う。

- **重要度**：`差し止め`、`重要`、`参考`。変更を承認する判断への影響を表す
- **状態**：`要判断`、`確認済み`、`未確認`。項目に必要な次の行動を表す

重要度や状態だけを表示せず、なぜその区分なのかと、確認に使うコードまたは検証を同じ場所へ置く。
すべての項目を同じ強さで見せず、差し止めと要判断を先に、確認済みと参考情報を後に置く。

各変更単位から、対応するコード比較や条件付き詳細へ直接移動できるようにする。
別の変更要約表や分類表で同じ内容を繰り返さない。
製品挙動を変えるコードを先に置き、テスト、ハーネス、文書、生成物は証拠として分ける。

## 4 条件付き詳細

責務別の変更を判断するために必要なものだけ置く。

1. **重要差分**：責務、ガード、interface、状態遷移が変わる実コードBefore / After
2. **実行フロー**：文章と差分だけでは追えない入力、分岐、外部I/O、失敗位置、出力
3. **契約と不変条件**：schema、設定、列挙値、拒否条件、複数箇所のガードが作る保証
4. **運用境界**：migration、feature flag、互換性、rollback、実環境や未変更consumer
5. **実験レポート**：比較実験を根拠にする場合の結論、例外、参照先

各詳細の冒頭に対応する変更単位と主要コードを示し、変更単位へ戻れるようにする。

### レビュー根拠の残し方

- Beforeにはbase SHA、対象path、該当行を示す。Afterにはcurrent commitまたはworking tree、対象path、該当行を示す。
- base側へ直接リンクできない場合は、その制約を明記し、現在のファイルへのリンクで代用しない。
- 実コード比較は、変更単位の主張を閉じる最小範囲へ絞る。importや周辺ノイズは省く。
- 各比較から、変更前後の責務、利用者または運用への効果、検証を追えるようにする。
- schema、設定、列挙値がinterfaceになる場合は、値、役割、適用範囲、拒否条件を表にする。
- 複数箇所で成立する保証は、不変条件からコードと検証へたどれるようにする。

## 5 検証と未確認事項

- 実施したコマンドと結果
- ケース別結果または手動確認手順
- 保証する範囲と保証しない範囲
- 失敗、未実施、環境差、追加確認が必要な事項

UIや実環境を含む手動確認では、期待結果と起きてはいけない結果を書く。
推定、実測、設定値、上限を区別する。

## 表示方針

- レビュー概要と変更単位は幅500px前後でも横スクロールなしで読むことができるようにする。
- 横スクロールは、interfaceやコード比較など列の対応自体が重要な箇所に限定する。
- 変更目的、差し止め、要判断を最初の視線範囲へ置き、確認済みと参考情報は後段へ置く。
- 見出し、順序、余白、ラベルで情報階層を作る。重要度や状態を色だけで区別しない。
- 一つの変更単位には一つの視覚的なまとまりを与え、カードの入れ子や過剰な装飾を避ける。
- 長いコード、契約、検証詳細は段階的に開示し、初期表示で判断に不要な情報を展開しない。
- 図は文章とコードより短く責務間の関係や処理経路を示せる場合だけ使う。図中の要素から変更単位と根拠へ移動できるようにする。
- 画像、SVG、カード、コード欄をビューポート外へはみ出させない。

## 小さな変更

単一モジュール内の小さな変更では、レビュー概要、一つの変更単位、検証と未確認事項だけでよい。
独立した変更マップ、コード比較、契約表、図は、判断に必要な場合だけ追加する。
