# 実装・検証レポート構成

## 00 索引兼レビュー結論

00だけで、何を変え、どこを読み、人間が何を判断するか分かるようにする。

### 変更の要約

- 対象PRまたは変更SHA
- 一文で示す変更目的
- 保証する範囲と保証しない範囲
- テスト件数などの主要な実測結果。分母と計測条件を併記する

### 実装地図

処理順の全体図と、責務ごとの実装領域を示す。
領域名は対象実装に合わせる。A、B、Cの記号を使う場合は、レポート全体で同じ意味に固定する。

各領域に次を置く。

- 何を変更したか
- 変更目的
- 主要コード
- 追加と削除を含む差分量、および全差分に占める割合
- 対応するフロー図、契約表、検証結果へのリンク

差分割合は工数、重要度、リスクの割合ではないと明記する。
テストと文書が差分を大きくしている場合は、実装、テスト、文書の内訳も示す。

### レビュー結果

レビュー単位はPR全体やファイルではなく、証明または判断を一つずつ閉じられる実装上の主張とする。

- **H**：仕様またはリスク許容を人間が決める。未決事項、確認済みの事実、選択肢、推奨を書く
- **P**：既存契約と実行結果で根拠が閉じている。人間が再確認しなくてよい理由と証拠を書く
- **U**：まだ確認していない。分かっていないこと、実行場所、確認を閉じる条件を書く

各主張に`H1`、`P1`、`U1`のようなIDを付ける。
実装領域を行、H/P/Uを列とする対応表を置き、各セルから個別主張へリンクする。
同じ表に、その領域を裏付ける01以降の章も示す。

## 01以降の根拠章

01以降は新しい論点を追加する場所ではない。
00に置いた実装領域とH/P/Uの根拠を、成果物が作られる順に展開する。
章番号と実装領域の記号が別の分類である場合は、その違いを00で明記する。

次の章から必要なものだけを使い、番号を詰める。

1. **変更目的**：変更前後、利用者に見える問題、保証範囲
2. **実行フロー**：入力、分岐、外部I/O、失敗位置、出力
3. **出力契約**：schema、必須値、正規化、参照整合性、拒否条件
4. **実効設定**：overrideとfallbackの優先順位、共有する利用経路
5. **コード責務**：変更前後の責務、主要関数、採用しなかった案
6. **検証**：SHA、コマンド、ケース別結果、実測値、回帰条件
7. **レビュー境界**：直接変更していないconsumer、実環境、運用、リリース条件

各章の冒頭に、対応する実装領域、主要コード、H/P/U IDを短く示す。
00の領域名または対応表へ戻れるリンクも置く。

## 図示方針

- 静止図だけで主要経路、分岐、終端が読めるようにする。
- 実行コストが異なる処理と外部I/Oを視覚的に分ける。
- 図から実装領域と詳細章へ移動できるようにする。
- 動きを使う場合は、方向、同時性、反復の理解を補う用途に限る。
- reduced-motionでも配線、状態ラベル、終端を残す。

## 短縮版

小さな実装では、00、該当する根拠章、検証、レビュー境界だけでよい。
ただし、変更目的、主要コード、実行した検証、保証しない範囲、H/P/Uのいずれかは省略しない。
