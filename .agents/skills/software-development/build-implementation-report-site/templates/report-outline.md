# レビュー用実装ブリーフの構成案

読者が「何が変わるか」「どのファイルが関係するか」「何に注意し、何を確認したか」を少ない読み返しで答えられる順に組み立てる。
節数、図、ナビゲーションの位置は変更の規模に合わせて選ぶ。

## 冒頭：変更の要約とファイル別説明

対象の役割と利用場面を示し、変更前の問題、変更後の挙動、利用者または運用への効果を短く説明する。
代表的な入力と出力が理解を助ける場合は一例を添える。内部名は読者向けの役割と対応付ける。
レビュー判断に影響する注意点、検証結果、重要な未確認事項を要約に残す。
根拠にない採用条件や判断事項を作らない。追加判断がなければ、そのためだけの欄を増やさない。

続けて、主要な変更ファイルを短い一覧で示す。

| ファイル・変更種別 | 何を変えたか | 影響・確認点 |
|---|---|---|
| 実際のpathと追加・変更・移動・削除 | ファイルの役割と変更内容 | 利用者への影響またはレビューで確認する点 |

多数の変更がある場合は目的別のまとまりへ整理し、テスト、生成物、文書の完全な一覧は詳細へ置く。
各変更ファイルが、いずれかの説明または証拠へ対応することを確認する。
配置の変更が重要な場合は最小のBefore / Afterツリーも使える。ツリーは全ての変更に強制しない。

## 必要な場合：処理全体の流れ

複数の処理段階やサービスにまたがる場合、ファイル一覧の後に、開始条件、主要な入出力、責務の受け渡し、終了を実行順に示す。
受付と完了、保存と適用、成功と失敗の停止点を区別する。
再実行や部分実行がある場合は、分岐条件、再利用・省略する処理、終了位置を示す。
短い番号付き説明で足りる場合はそれを使う。図は文章より関係や分岐を簡潔に示せる場合に使う。
各段階から対応する変更の詳細へつなぎ、実コード差分と検証証拠を保持する。

## 本文：変更目的ごとの説明・差分・検証

一つの効果を実現する関連ファイルをまとめ、一つの目的を順にレビューできるようにする。
製品挙動を変える中核の変更から説明し、その根拠になるテスト、生成物、文書へつなぐ。
各まとまりでは次を追えるようにする。小さな変更で全項目を独立した節にする必要はない。

- 変更前と変更後の挙動、必要な入力、拒否条件、副作用、状態遷移
- 変更を実現する主要ファイルと、判断に必要な実コードBefore / After
- 利用者または運用への効果、注意点、変えていない境界
- 検証結果と直接保証する範囲、未実施・失敗・未確認の事項

同じ処理順や数値の説明を、別の要約表、図、詳細章で重ねない。
図と表を併用する場合は、図を処理関係、表を契約の対応など異なる説明に使う。
ナビゲーションが必要なら、変更目的への目次やサイドナビを選ぶ。配置を固定しない。

## 詳細：根拠を確認できるように残す

- Beforeはbase SHAまたは提供された変更前snapshot、Afterはcommitまたはworking treeと対象pathへ追跡できるようにする。未提示のSHAは作らない。
- BeforeとAfterの参照先を同じ変更後ファイルで代用しない。参照できない場合は制約を記す。
- コード差分は主張を確認できる最小範囲へ絞る。分岐、ロック、transaction、拒否処理などの根拠は省略しない。
- コードの移動と内容変更を分け、移動前後のpath、内容、呼び出し元への影響を示す。移動しただけのコードを新しい処理として説明しない。
- schema、設定、API値、alias、拒否条件などが契約になる場合は、対応と適用範囲を示す。
- 横断的な保証は、成立させるコードと検証へ結ぶ。不変条件の件数や識別子は固定しない。
- テストごとに固定する契約、前提、操作、期待結果を実ファイルpathへ結ぶ。目的や共通操作が同じなら重ねて書かない。
- 検証結果と保証範囲は本文に残す。長いテスト差分、完全なログ、生成物は折りたたむかリンクする。テストや生成物自体が重要な契約を変える場合は、意味のある変更を本文にも示す。
- 実装、自動テスト、ローカルE2E、未確認を区別する。API fieldのテストだけからUIや後続処理まで確認済みとは書かない。
- 比較実験が根拠なら、既存の結果、ログ、レポートへつなぐ。詳細を再構成して数値や比較対象をずらさない。

## 表示と読み返しの確認

冒頭から結論、主要な変更ファイル、重要な注意点を見つけられるかを確認する。
本文からコードと検証へ到達できることを確かめ、長いコードや表の横スクロールは部品内に収める。
小画面でページ全体が横へ延びないこと、折りたたみを開いても重要な対応を読めることを確認する。
色だけで変更種別や検証状態を区別しない。
短い文章、統一された部品、折りたたみの数だけで認知負荷の低さを実証したとは扱わない。
人手の評価では、変更の挙動、関連ファイル、注意点、検証範囲を正しく説明できるかを確認し、読み返しや所要時間は測った場合だけ記録する。
