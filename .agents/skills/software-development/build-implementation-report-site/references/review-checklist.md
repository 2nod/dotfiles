# 実装レポートSiteのレビューチェックリスト

## ノーコンテキストで読めるか

- PR、issue、会話を開かずに、対象の役割を一文で説明できるか。
- 誰が、どの場面で使う変更かが分かるか。
- 代表的な入力と出力、または具体的な利用場面を一つ示したか。
- 内部名や略語を、読者向けの名称と対応付けてから使ったか。
- 各主要コードについて、パスだけでなく責務と確認点を書いたか。
- コードの変更、挙動が変わる理由、利用者または運用への効果を因果で追えるか。
- 「今回」「前述」「追加対応」など、レポート外の経緯がないと意味が定まらない表現を除いたか。

## 変更マップ

- `git diff --name-status` 相当のbaseからの変更と、tracked、untrackedの状態を確認したか。
- 変更ファイルを責務へ対応付け、追加、変更、移動、削除を区別したか。
- 各変更領域について、全体の中で担う役割を実コード、設定、参照関係から確認したか。
- 入口、呼び出し先、interface、設定、テストなど、変更の理解に必要な近接要素を示したか。
- 製品ロジック、運用スクリプト、テスト、生成物を責務別に分けたか。
- baseからの各変更ファイルが、いずれかの変更単位または証拠へ対応しているか。
- 全リポジトリのtreeや、役割を説明しない全ファイル一覧を置いていないか。
- ディレクトリ構成を変えた場合、baseと変更後の最小構成から移動や責務境界の変化を追えるか。
- 単一モジュール内の小さな変更で、不要な独立マップを作っていないか。

## 根拠

- base SHAと変更後の参照を記録したか。変更後が未commitならworking treeとdirty状態、commit済みならSHAを示したか。
- 説明した処理順を実コードで確認したか。
- 設計文書と実装が食い違う場合、実装を事実として示し、差分を隠していないか。
- 推定結果を実測結果として書いていないか。
- 実装済み、検証済み、今後の案を同じ強さで書いていないか。

## レビュー概要

- 最初の画面が5分で読めるレビュー用実装ブリーフになっているか。
- 変更目的、利用者または運用への効果、判断事項、主なリスク、検証結果を最初に確認できるか。
- 差し止め、要判断、未確認の項目がある場合、対応する変更単位へ直接移動できるか。
- 対象の役割、利用者、発火条件、代表的な入力と出力を、変更の解釈に必要な範囲で示したか。
- 製品の実行時挙動の変更と、テスト、文書、レポート、検証ハーネスの変更を分けたか。
- 差分割合を出す場合、分母を示し、工数やリスクの割合ではないと明記したか。
- 概要と詳細で、保証範囲、用語、件数、未確認事項が一致しているか。
- 複数の責務にまたがる保証がある場合、レビュー概要の少数の不変条件から変更単位、コード、テストへたどれるか。

## 責務別の変更

- 変更をファイル単位ではなく、一つの効果をもたらす責務単位へまとめたか。
- 各変更単位で役割と目的を別々に示し、入力、判定・防御、出力、Before / After、テスト証拠をこの順に追えるか。
- 各変更単位について、実装、自動テスト、ローカルE2E、未確認・追加推奨を別々に示したか。
- 部分的に確認した変更単位を、対象を限定せず「確認済み」と表示していないか。
- 各レビュー項目に、重要度、状態、区分した理由、コードまたは検証根拠があるか。
- 重要度は差し止め、重要、参考、状態は要判断、確認済み、未確認として別々に判断しているか。
- 差し止めと要判断が先に見え、確認済みや参考情報との濃淡があるか。
- 重要度や状態を、理由のない色や記号だけで表していないか。
- 変更単位がコード比較や条件付き詳細への唯一の導線になっているか。
- 同じ変更を変更要約表、分類表、詳細で繰り返していないか。
- 製品挙動を変えるコードを先に、テスト、ハーネス、文書、生成物を証拠として示したか。
- 複数の変更単位がある場合、右サイドナビから各変更単位へ移動できるか。
- サイドナビに一行の役割と検証状態があり、本文の詳細を複製していないか。
- 用語集を変更単位ナビへ混ぜず、本文の前提または背景で折りたたんだか。

## 条件付きの根拠

- 責務、ガード、契約、状態遷移が変わる場合だけ、baseと変更後の実コードBefore / Afterを置いたか。
- Beforeはbase SHA、path、該当行、Afterはcurrent commitまたはworking tree、path、該当行へ追跡できるか。
- BeforeとAfterの参照先を同じ変更後ファイルで代用していないか。
- 各コード比較から、変更前の責務、変更後の責務、利用者または運用への効果を読み取れるか。
- importや周辺ノイズを省きつつ、分岐条件、ロック、transaction、拒否処理など主張の根拠を隠していないか。
- 全変更ファイルを機械的に比較せず、主張を閉じる最小の差分へ絞ったか。
- schema field、API値、設定、正規化aliasなど列挙値が契約になる場合、役割、適用範囲、拒否条件を確認できるか。
- 複数箇所で成立する競合防止、再送安全性、完全一致検証などがある場合、不変条件からコードと検証へたどれるか。
- 既存レポートの再構成時に高信号な根拠を棚卸しし、古い証拠だけを更新して、現在も有効な根拠を維持したか。

## テスト証拠

- 目的と共通の操作を変更単位に一度だけ置いたか。
- 各テストケースに、そのケースが防ぐ事故または固定する契約を「検証意図」として示したか。
- 検証意図が、変更単位の目的、前提、期待結果の言い換えになっていないか。
- 前提と期待結果をテストケースごとに対応付けたか。
- 共通の操作が、どの前提と期待結果に適用されるかが明確か。
- テスト証拠に実ファイルのpathと、必要な場合はcase名または行番号があるか。
- 期待結果に成功状態だけでなく、拒否時に起きない副作用も含めたか。
- API fieldのテストだけを根拠に、UI表示や後続処理まで自動テスト済みと書いていないか。
- テスト件数だけを実装の証拠としていないか。

## 用語

- レポート単体で意味が分かる用語か。
- 内部変数名、ログシグナル、古い設計名を説明なしで使っていないか。
- 似た概念を同一視したり、根拠のない包含関係を作ったりしていないか。
- 直訳調の内部語を、利用者が判断できる具体的な日本語へ直したか。
- 異なる入力、状態、境界、計測対象を同じ名前で扱っていないか。

## 処理フロー

- 上から下へ実行順を追えるか。
- YESとNOの分岐先に矢印があり、合流または終了位置が分かるか。
- ループの戻り先と継続条件が分かるか。
- 計画、評価、適用など実装上別の操作を、同じ処理に見せていないか。
- 同じ処理を二度適用しているように見えないか。
- 早期終了、安全上限、最終手段が何をするか説明したか。
- 図の各段階に、対象、処理、次へ進む条件があるか。

## 図示

- 実装上の状態と遷移から図の要素を導出したか。
- 静止図だけで主要な経路、分岐、終端が読めるか。
- 図の要素から対応する主張、コード、検証へたどれるか。
- 動きを使う場合、`software-development/technical-flow-diagrams` の検証条件を満たしたか。

## 実行コスト

- 計算だけで済む処理と、外部I/Oや副作用を伴う処理を分けたか。
- 実行の目的と発火条件を分けて書いたか。
- 初回実行と追加実行を分け、計数式を示したか。
- 回数には「1ケースあたり」などの分母があるか。
- 平均値だけでなく、ケース別の分布または代表経路を示したか。
- 通常の目安、再試行、安全上限を区別したか。
- 回数や時間を変える設定を計測条件に書いたか。

## 実験レポートとの接続

- 比較実験を根拠にする場合、実験レポートのrun ID、variant ID、採用基準、結論を参照できるか。
- 実装レポートの要約と実験レポートの結果が同じ比較対象を指しているか。
- 実験の全ケースや詳細な計測条件を重複掲載せず、レビュー判断に必要な結論と例外へ絞ったか。
- 実験レポートがない場合、比較結果を実測として断定していないか。

## 情報設計と文章

- 会話や作業経緯を知らない新規参加者が、レポート単体で対象と結論を理解できるか。
- 追記の積み重ねではなく、確定した契約と処理順に沿って全体を再構成したか。
- 「前回」「追加対応」など、レポート外の経緯を参照する文が残っていないか。
- 冒頭だけで変更の目的、結果、判断事項が分かるか。
- 変更目的、変更マップ、責務別の変更、条件付き詳細、検証の順に読めるか。
- スクリプトとテストをロジック本体と同列の変更として扱っていないか。
- 全パスを列挙せず、主要な実装場所だけを示したか。
- 詳細を削る代わりに重要な根拠まで失っていないか。
- 変更を説明するためだけの設計書的な章を増やしていないか。
- 見出しが抽象語だけになっていないか。
- 不自然な日本語、英語混じり、略語、指示語を読み直したか。
- 同じ説明を別の節で繰り返していないか。

## 表示と公開

- 色を増やしすぎず、同じ役割は同じ見た目になっているか。
- 変更目的、差し止め、要判断が最初の視線範囲にあり、確認済みと参考情報より強く見えるか。
- 見出し、順序、余白、ラベルだけでも情報階層と重要度を判別できるか。
- 色だけに重要度、状態、成功、失敗の意味を持たせていないか。
- 一つの責務単位が一つの視覚的なまとまりになり、カードを入れ子にしていないか。
- 長いコード、契約、検証詳細を段階的に開示し、初期表示の情報量を抑えたか。
- 分岐内の段階が主フローと同じ視覚言語を使っているか。
- デスクトップとモバイルで矢印と順序が保たれるか。
- レビュー概要と責務別の変更は幅500px前後でも横スクロールなしで読めるか。
- ビルド、lint、表示内容の自動テストが通るか。
- 実ブラウザで見出し、折り返し、画像、リンクを確認したか。
- 公開ソースのcommit SHAとSiteバージョンが一致するか。
- 公開URLを報告し、作業ツリーの未コミット変更を確認したか。
- レポートと検証画像が製品リポジトリ外にあるか。
- レポートがstage、commit、PR差分へ入っていないか。
- ローカル成果物の場合も、最終回答に絶対パスを示したか。
