# 実装レポートのレビューチェックリスト

## 読者が最初に判断できるか

- 会話を知らずに、対象の役割と変更後の挙動を説明できるか。
- 利用者または運用への効果が、具体的な入力・出力や利用場面から分かるか。
- 冒頭に主要な変更ファイルの役割、変更内容、影響または確認点があるか。
- 注意すべき変更、検証結果、重要な未確認事項を冒頭から見つけられるか。
- 入力にない採用基準、リスク、追加判断を作っていないか。

## ファイルと変更目的を対応付けたか

- baseからのtrackedとuntrackedの変更を確認し、追加、変更、移動、削除を区別したか。
- 一つの目的を実現する関連ファイルを、同じまとまりで説明したか。
- ファイル名だけで説明を済ませず、役割と挙動への影響を書いたか。
- 全変更ファイルが、本文または詳細の証拠へ対応しているか。
- コード移動と内容変更を区別し、呼び出し元や設定への影響も確認したか。
- テスト・生成物が契約を変える場合、その意味を要約から隠していないか。

## 主張と根拠を追えるか

- BeforeとAfterの版・pathを区別し、未提示のSHAや実行事実を作っていないか。
- 重要な挙動、拒否条件、副作用、状態遷移の説明を実コードで確認できるか。
- 説明用の図やスケッチと、実コード差分を区別したか。
- テストの前提、操作、期待結果、固定する契約を実ファイルへ結んだか。
- 実装、自動テスト、ローカルE2E、未確認を区別したか。
- テストが直接確認した範囲を越えて、UIや実運用の成立を断定していないか。
- 既存レポートの有効な証拠を残し、古い件数や保証だけを更新したか。

## 読み返しを減らせる構成か

- 必要な全体フローがファイル一覧の後にあり、受付と完了、保存と適用、失敗時の停止点を追えるか。
- 一つの変更目的から実コードと検証へ直接進めるか。
- 題名、要約、表、図、本文が同じ説明を繰り返していないか。
- 結論と検証結果は見せ、長いコード・ログ・生成物を必要時に読めるようにしたか。
- 変更規模に合わない節、ツリー、右サイドナビを増やしていないか。
- 詳細を折りたたんだ結果、悪化、失敗、重要な注意点、未確認を隠していないか。
- 短さや指定レイアウトへの一致だけを、読みやすさの合格条件にしていないか。

## 表示と保存を確認したか

- `writing/html`の本文と部品見本を読み、共有CSSと必要なアセットを同梱して読み込んだか。
- 独自CSSが配置調整に収まり、コード強調、差分、印刷などの既存表示要件を保持したか。
- 実ブラウザでリンク、ID重複、デスクトップと小画面を確認したか。
- 長いpath、ハッシュ、表、コードがページ全体を横へ広げていないか。
- 折りたたみを開いても根拠と本文の対応を読めるか。
- 色だけに変更種別や検証状態の意味を持たせていないか。
- 実施していない描画検証や人手の理解度評価を、完了したと書いていないか。
- レポートと画像が製品リポジトリ、stage、commit、PRへ入っていないか。
- 最終回答に保存先と、必要な未確認事項を示したか。
