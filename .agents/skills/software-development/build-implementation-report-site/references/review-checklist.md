# 実装レポートSiteのレビューチェックリスト

## ノーコンテキストで読めるか

- PR、issue、会話を開かずに、対象の役割を一文で説明できるか。
- 誰が、どの場面で使う変更かが分かるか。
- 代表的な入力と出力、または具体的な利用場面を一つ示したか。
- 内部名や略語を、読者向けの名称と対応付けてから使ったか。
- 各主要コードについて、パスだけでなく責務と確認点を書いたか。
- コードの変更、挙動が変わる理由、利用者または運用への効果を因果で追えるか。
- 「今回」「前述」「追加対応」など、レポート外の経緯がないと意味が定まらない表現を除いたか。

## 根拠

- baseと変更後のcommit SHAを記録したか。
- 説明した処理順を実コードで確認したか。
- 設計文書と実装が食い違う場合、実装を事実として示し、差分を隠していないか。
- 推定結果を実測結果として書いていないか。
- 実装済み、検証済み、今後の案を同じ強さで書いていないか。

## 00のレビュー導線

- 00が5分で読めるレビュー用実装ブリーフになっているか。
- 00の先頭が、読み始めるための文脈、変更目的、主要なBefore / Afterと目的、変えていない境界、レビュワーの判断事項、検証結果の順で読めるか。
- 製品の実行時挙動の変更と、テスト、文書、レポート、検証ハーネスの変更を分けたか。
- 主張ごとに、コードの責務、挙動へ効く理由、検証結果、判断事項を一行で追えるか。
- 差分割合を出す場合、分母を示し、工数やリスクの割合ではないと明記したか。
- H/P/Uや実装領域記号を使う場合、初出で定義し、読者向け名称を併記したか。
- H/P/Uを使う場合、Humanは方針選択、Provenは記載範囲内の確認済み、Unconfirmedは追加証拠で解消可能な未確認として扱っているか。
- Unconfirmedを不具合の断定として扱っていないか。
- 詳細を置く場合、00の主張から該当コードや検証へリンクできるか。
- 00と補足で、保証範囲、用語、件数、未確認事項が一致しているか。

## 条件付きの根拠

- 責務、ガード、契約、状態遷移が変わる場合だけ、baseと変更後の実コードBefore / Afterを置いたか。
- Beforeはbase SHA、path、該当行、Afterはcurrent commitまたはworking tree、path、該当行へ追跡できるか。
- BeforeとAfterの参照先を同じ変更後ファイルで代用していないか。
- 各コード比較から、変更前の責務、変更後の責務、利用者または運用への効果を読み取れるか。
- importや周辺ノイズを省きつつ、分岐条件、ロック、transaction、拒否処理など主張の根拠を隠していないか。
- 全変更ファイルを機械的に比較せず、主張を閉じる最小の差分へ絞ったか。
- schema field、API値、設定、正規化aliasなど列挙値が契約になる場合、役割、適用範囲、拒否条件を確認できるか。
- 複数箇所で成立する競合防止、再送安全性、完全一致検証などがある場合、不変条件からコードと検証へたどれるか。
- 既存レポートの再構成時に高信号な根拠を棚卸しし、古い証拠だけを更新して、現在も有効な根拠を維持したか。

## 用語

- レポート単体で意味が分かる用語か。
- 内部変数名、ログシグナル、古い設計名を説明なしで使っていないか。
- 似た概念を同一視していないか。例として、吹き出し外テキストとオノマトペは別の分類である。
- 「安全予算」「劣化許容はしご」のような直訳調の語を、具体的な日本語へ直したか。
- テキスト領域、行領域、吹き出し領域など、異なるbboxを区別したか。

## 処理フロー

- 上から下へ実行順を追えるか。
- YESとNOの分岐先に矢印があり、合流または終了位置が分かるか。
- ループの戻り先と継続条件が分かるか。
- 候補の計画、再計算、適用を別の操作として正確に書いたか。
- 同じ処理を二度適用しているように見えないか。
- 早期終了、安全上限、最終手段が何をするか説明したか。
- 図の各段階に、対象、処理、次へ進む条件があるか。

## 図示

- domain stateからtimeline/event、view model、SVGへ導出したか。
- 静止図だけで主要な経路、分岐、終端が読めるか。
- 動きが装飾ではなく、方向、同時性、反復の理解に寄与しているか。
- wireと移動対象のgeometry sourceが一致しているか。
- `prefers-reduced-motion`でも説明が成立するか。
- 画面外停止、speed、FPS制御が必要な図で確認したか。
- 特定状態をレビューするための時刻固定またはstate固定手段があるか。

## 実行コスト

- 計算だけで済む処理と、外部I/Oや実レンダリングを伴う処理を分けたか。
- 実行の目的と発火条件を分けて書いたか。
- 初回実行と追加実行を分け、計数式を示したか。
- 回数には「1ケースあたり」などの分母があるか。
- 平均値だけでなく、ケース別の分布または代表経路を示したか。
- 通常の目安、再試行、安全上限を区別したか。
- `skip_line_break`など、回数を変える設定を計測条件に書いたか。

## 比較実験

- baseと変更後で、入力、フォント、画像、renderer、ハーネス、設定が一致しているか。
- 古いworktreeや古いmainを比較対象にしていないか。
- 実レンダーを主張する場合、実際のCapture APIまたは描画系を使ったか。
- 解消前、base後、変更後の画像を同じ条件で並べたか。
- 品質を解消率だけでなく、移動量、縮小量、はみ出しなどでも確認したか。
- 合計回数だけで改善を主張せず、ケースあたりの値を示したか。
- コマンド、入力、resultsを追跡できる形で一時成果物へ残したか。

## 情報設計と文章

- 会話や作業経緯を知らない新規参加者が、レポート単体で対象と結論を理解できるか。
- 追記の積み重ねではなく、確定した契約と処理順に沿って全体を再構成したか。
- 「前回」「追加対応」など、レポート外の経緯を参照する文が残っていないか。
- 冒頭だけで変更の目的、結果、判断事項が分かるか。
- 結論、レビュー導線、重要差分、検証の順に読めるか。
- スクリプトとテストをロジック本体と同列の変更として扱っていないか。
- 全パスを列挙せず、主要な実装場所だけを示したか。
- 詳細を削る代わりに重要な根拠まで失っていないか。
- 変更を説明するためだけの設計書的な章を増やしていないか。
- 見出しが抽象語だけになっていないか。
- 不自然な日本語、英語混じり、略語、指示語を読み直したか。
- 同じ説明を別の節で繰り返していないか。

## 表示と公開

- 色を増やしすぎず、同じ役割は同じ見た目になっているか。
- 分岐内の段階が主フローと同じ視覚言語を使っているか。
- デスクトップとモバイルで矢印と順序が保たれるか。
- 冒頭の変更要約は幅500px前後でも横スクロールなしで読めるか。
- ビルド、lint、表示内容の自動テストが通るか。
- 実ブラウザで見出し、折り返し、画像、リンクを確認したか。
- 公開ソースのcommit SHAとSiteバージョンが一致するか。
- 公開URLを報告し、作業ツリーの未コミット変更を確認したか。
- レポートと検証画像が製品リポジトリ外にあるか。
- レポートがstage、commit、PR差分へ入っていないか。
- ローカル成果物の場合も、最終回答に絶対パスを示したか。
