# 実装レポートSiteで避ける失敗

## 結論から作り始める

**症状**：実装確認より先に図や説明を書き、後から処理順、用語、計測条件を何度も修正する。

**対処**：最初にbaseと変更後のコード、設計文書、テスト、計測結果を読む。説明ごとに根拠となる関数、設定、結果を対応づけてから画面を作る。

## レポートを製品docsへ置く

**症状**：一時的な検証レポート、改善方針、画像比較を恒久的な製品docsへ追加する。

**対処**：長期保守する仕様と設計だけを製品docsへ残す。比較結果は`tmp`、レビュー用HTMLは専用Siteへ分ける。既存レポートを別目的へ流用せず、目的が違う場合は新しいレポートを作る。

## 変更範囲を一列に並べる

**症状**：ロジック本体、スクリプト、テスト、レポートを同じ重要度で列挙し、何が製品挙動を変えるのか分からない。

**対処**：ロジック本体を先に説明し、ハーネスとテストは証拠と回帰防止として分ける。パスは主要な実装場所だけを示す。

## 図が実装にない段階を作る

**症状**：説明用の番号やphase名が、実装上の識別子に見える。上段と分岐内でカードの見た目が変わり、処理順を追えない。

**対処**：実コードにない番号を付けない。主経路と分岐で同じ視覚言語を使い、矢印、終了、合流、戻り先を明示する。

## 計画と適用を同じ動詞で書く

**症状**：「位置調整」の後に再び「位置調整」が現れ、二度移動しているように見える。

**対処**：「候補を計画」「同じ条件で再計算」「候補を適用」を区別する。二重適用や二重レンダリングではない場合は、その場で明記する。

## 分岐条件だけを書き、理由を書かない

**症状**：「候補あり／なし」の意味と、なぜそこで分けるのかが分からない。

**対処**：条件を判定式に近い言葉で書き、各分岐で省く処理、先に試す処理、品質上の理由を一文ずつ示す。

## 内部語を見出しに使う

**症状**：ログ名、変数名、直訳語だけが表示され、文脈なしでは意味が分からない。異なる分類を同一視する。

**対処**：読者が知りたい結果へ訳す。内部名は補助として併記する。似た概念は別々に定義し、包含関係を推測で作らない。

## 実行目的と条件を混ぜる

**症状**：「確認のためレンダリングする」とだけ書き、いつ発火するのか分からない。

**対処**：「目的：解消確認」「実行条件：推定重なり面積が0以下」のように分ける。計算だけで採用する経路も併記する。

## 初回処理と追加処理を同じ回数にする

**症状**：「実レンダリング1.4回」と書くが、初回描画を含むか分からない。

**対処**：`全体回数 = 初回1回 + Resolver追加回数`のように計数式を書く。改善対象の指標名を「追加レンダリング」とする。

## 平均値だけで改善を示す

**症状**：ケース数に依存する合計や平均だけを示し、通常経路が何回か分からない。

**対処**：ケース別の分布、衝突ありだけの値、0回、1回、2回、通常目安超過、安全上限を分ける。「複数段階」のような抽象語は「通常縮小後に移動」のような実経路へ置き換える。

## 計測条件を後から足す

**症状**：`skip_line_break`、レンダリング上限、renderer、入力画像など、回数を左右する条件が結果の近くにない。

**対処**：指標の直下と検証節の両方に条件を書く。計測外の段階はフロー上で「参考」と明示し、実測値へ混ぜない。

## 異なる実装を比較する

**症状**：古いworktree、更新前のmain、異なるCapture API、異なる入力を比較し、改善値の意味がなくなる。

**対処**：比較直前にSHAと作業ツリーを確認する。baseと変更後でハーネス、入力、フォント、画像、renderer、設定を固定する。

## 結果画像が解消後だけになる

**症状**：変更後の画像だけを載せ、何が改善したか判断できない。

**対処**：同じ入力の解消前、base後、変更後を並べる。解消率だけでなく、移動量、縮小量、はみ出しも添える。

## 公開したSiteとソースがずれる

**症状**：未pushのソースや別commitのアーカイブを公開し、レビュー対象と説明が一致しない。

**対処**：検証済みソースをpushし、その完全SHAからSiteバージョンを保存する。デプロイ完了後にURLとcommitを確認する。
