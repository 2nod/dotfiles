# 調査チェックリスト

図を描く前に確認する。埋まらない項目は、ページ上で「未確認」と書く。空欄を推測で埋めない。

## 事実と推論の分離

読んだコードから確認できたことだけを事実として扱う。
次はいずれも推論であり、事実として書かない。

- 命名から推測した責務
- コメントやドキュメントの記述で、実装を読んでいないもの
- 「たぶんこうなっている」で補った分岐
- 実行して確かめていない性能特性や上限

推論をページに載せる場合は、根拠と確かめ方を併記する。
載せる価値がなければ落とす。

## 1周の確定

入口から出口までを、分岐せずに1本で語れる経路を先に決める。
この経路が読者の背骨になる。決まらないうちに詳細図を描かない。

- 入口は何か（HTTPリクエスト、cron、イベント、ユーザー操作）
- どこで状態が変わるか
- どこで外部システムに出ていくか
- 出口はどこか（レスポンス、永続化、通知）

## 省略しやすい層

正常系だけを描いた図は、読者に誤った安心を与える。次を各項目ごとに確認する。

**失敗**
- どの段が失敗しうるか
- 失敗はどこまで伝播するか。握り潰す箇所はあるか
- 部分的に成功した状態は残るか

**再試行**
- 誰が再試行するか（呼び出し側、キュー、外部サービス）
- 再試行で重複が起きるか。冪等性はどこで担保されるか
- 上限と間隔

**権限**
- 誰がこの経路を起動できるか
- 認証と認可のどちらをどこで行うか
- 権限判定を通らない経路（内部呼び出し、管理用、webhook）があるか

**永続化の境界**
- どのデータがどこに残るか。具体的な保存先を書く
- 揮発するもの（メモリ、キャッシュ）と残るものの境界
- 削除や期限はあるか

## 実装アンカー

比喩を使った段には、必ず実装へ戻る手掛かりを併記する。
読者が自分でコードを開けることが条件になる。

- ファイルパス
- 関数名、クラス名
- endpoint（メソッドとパスの両方）
- テーブル名、コレクションのパス、キーの形
- 外部サービス側の識別子

抽象名詞だけの段（「データを処理する」「情報を保存する」）は、アンカーが無い印と考える。
